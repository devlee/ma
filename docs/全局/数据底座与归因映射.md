# 数据底座与归因映射需求

> 版本：v0.1（按灵策总装图整理）
> 数据底座是整个灵策体系的地基：所有决策、执行、结果数据在这里落库，并且**事后对得上账**。归因映射解决的核心问题一句话：**"这个结果是哪个动作带来的"——防各说各话。**
> 全局机制归属《灵策总纲》第 5 节（概要），本册是字段与规则级定义。

---

# 1. 背景与目标

## 1.1 要解决的问题

- **动作和结果对不上**：换了图、调了价、发了邮件，GMV 变了——不知道是谁的功劳/责任，各团队各讲各的故事。
- **口径各算各的**：同一个"转化率"三个报表三个数。
- **决策本身没有留痕**：批了什么、什么时候批的、依据是什么，散在聊天记录里。

## 1.2 目标

- 三类数据全部落库、互相挂得上：决策事件、执行结果、商城结果。
- 每条执行记录带**意图单编号**，归因有唯一主键。
- 口径只认 L1 指标树，底座不自定义任何口径。

# 2. 三类记录

| 类 | 内容 | 谁写入 | 关键字段 |
|---|---|---|---|
| 决策事件 | 意图单下发、审批确认、规划锁定、配置变更、假设状态变更 | 灵策自己 | 时间戳、操作人、意图单编号/对象、依据（留痕条格式） |
| 执行结果 | 实际干了什么：改了哪张图、调了什么价、发了哪封邮件、活动何时上线 | 执行系统回传 或 人工工作台回填 | **意图单编号（必带）**、对象、动作类型、完成时间戳 |
| 商城结果 | 平台产出：流量、加购、订单、GMV、退款 | 商城数据接入 | 键 = **站点 + SKU + 时间**（天然不带意图单编号） |

通用规矩：**指标带站点（默认=全站）、动作带时间戳、口径以 L1 为准。**

# 3. 归因映射：两跳链路

```
决策事件 ──第一跳（强链接）──→ 执行结果 ──第二跳（弱链接）──→ 商城结果
          意图单编号直接传              按"对象 + 时间窗"锚定
```

- **第一跳：决策 → 执行**。强链接：执行记录必带意图单编号，没有编号的执行记录视为脏数据（人工工作台回填界面强制填编号）。
- **第二跳：执行 → 商城**。弱链接：商城数据没有编号，靠**事件锚定**挂上——执行完成时间戳在对象（站点×SKU）的时间线上画一根竖线，商城数据按竖线前后切窗对比。这是换图判定引擎"事件锚定 + 品类同期校正"机制推广为全系统规矩。

# 4. 多动作叠加（归因的难点）

同一 SPU 同期换了图、调了价、进了活动——GMV 涨了算谁的？

**v1 原则：不强制分摊、强制记账。**

1. 每条商城结果关联**同期生效动作集**：窗口内所有在场意图单的编号都挂上，一个不漏。
2. 单动作效果判定时，**显式标注干扰项**（"判定期内该 SPU 另有调价动作"），判定结论带不确定性说明——判定引擎现行做法，全域沿用。
3. **比例分摊口径预留在 L1**（归因与分摊口径，第四样），v1 不启用。理由：分摊模型做错比不做更危险——会给错误归因盖上"系统算的"的章。先保证每笔结果"知道当时谁在场"，分摊等数据和需求成熟再上。

# 5. 横向对象的落账

渠道、风格库、供应商、服务线不在对象树上，它们的成本和结果要参与经营分析，必须能摊到**站点×品类**：

- 渠道花费 → 站点×品类（营销域启动时最急，分摊规则登记进 L1）
- 风格库：战绩按使用该风格的 SPU 聚合（已有机制）
- 供应商成本、服务成本：后续随域启动定义

# 6. 数据需求清单

| 数据 | 粒度 | 现状 |
|---|---|---|
| 商城结果（流量/加购/订单/GMV/退款） | 站点 × SKU × 日 | 已有（快照体系），键格式需统一核验 |
| 执行结果（灵枢侧：修图/换图/买家秀） | SPU × 动作 × 时间戳 | 已有，需补意图单编号字段 |
| 执行结果（灵犀/鹊桥侧） | 对象 × 动作 × 时间戳 | 随系统对接定义回传字段 |
| 执行结果（人工工作台回填） | 对象 × 动作 × 时间戳 | 新建（待办中心回填表单） |
| 决策事件 | 全部决策对象 | 新建（留痕条格式落库） |
